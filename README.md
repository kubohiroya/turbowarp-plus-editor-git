# TurboWarp Plus Editor Git

[日本語](README.ja.md)

Local Git adds a panel to the TurboWarp Plus Editor. Select the repository root once, then browse to an sb3-toolchain v1 project folder inside it. Project editing and saving are supplied by the Editor's project-folder integration.

The panel opens from a branch button in the Editor's menu bar. `mountGitPanel({vm, document, host})` mounts the panel and returns `{open(locale), refresh(), dispose()}`; `renderBranchButton(createElement, {vm, locale})` renders the button for the panel mounted for `vm`, and renders nothing while there is none (such as when the host does not offer local Git). The button shows a branch icon, the current branch and ▾. Before a repository is chosen it reads **Git** and offers **Choose Repository…**; a detached HEAD shows its short commit ID, and a branch without records yet says so. Its menu (`role="menu"`; arrow keys, Home and End, Enter, Escape back to the button) lists the local branches with the current one checked, then **Create and switch to …** for `origin` branches without a local one, **New Branch…** (a small form that creates a branch at HEAD, switching to it by default) and **Open Local Git**. The button and the panel share one repository and the same operations, so switching from the menu asks and refuses exactly as the panel's own buttons do. The result shows in a snackbar at the bottom of the window instead of opening the panel: **Switched branches.** with **Reload Project** when a project folder is selected in the panel, **Created the branch.**, or the panel's reason for a refusal (as an alert) with **Open Local Git**. A declined confirmation shows nothing. The snackbar hides after six seconds unless it is hovered or focused, Escape or its close button dismisses it, a new one replaces the old, and focus is not moved into it (Tab reaches its buttons). Without `localWrite` the menu lists the branches only. The button follows branch changes made in the panel or by other tools: while the panel is out of view, the panel's checks below read only HEAD and the branch refs. `BranchButton` is the button on its own, for hosts that keep the state themselves.

For a side panel of the host, `renderHistoryView(createElement, {vm, locale})` draws the history graph of the same repository. It reads the history again whenever the branches move, offers the graph's branch actions when the host allows writes and tells their results in the same snackbar; before a repository is chosen it offers **Choose Repository…**, and it renders nothing while no panel is mounted for `vm`. `followChangeMarks(vm, directory, listener)` calls `listener` with the Git status of the files under `directory` (`added`, `modified`, `deleted` or `untracked`, by path relative to `directory`) as the panel last read them, for a folder explorer, and returns the function that stops it. `changeMarks(changes, folder)` is the mapping on its own.

The panel separates staged, unstaged, and untracked changes. It shows the current branch, HEAD, local branches, and the history. Select a file to inspect its text diff or binary size. When the host supplies a block renderer, project data (`project.source.json`) is compared as blocks by stage, sprite and code, and **Text** switches to the line diff. Costume and backdrop comparisons read assets from the compared versions: HEAD and the index for staged changes, the index and the working tree for unstaged changes, the working tree for untracked files, and the first parent and the commit for history. The assets folder is the `assetsDirectory` of that version's `sb3-source.json` (`assets` by default). Pull request reviews read assets from raw.githubusercontent.com at the merge base and head, without using the GitHub API rate limit. A review's **Reviewed** marks are kept in browser storage per repository and pull request, together with each script's content: they survive closing the panel and reloading the Editor, and only the marks of scripts whose content changed are cleared when the pull request head moves. They are never written to project files or Git. Select a commit to compare its files with its first parent. The selected project limits the file list and diffs to that folder.

While the panel is open, it checks the repository every two seconds, when the window regains focus, and on `FileSystemObserver` notifications where available. It compares the sizes and modification times of HEAD, the index, `packed-refs`, `config`, the current branch ref, and the files in the selected project folder (the whole work tree when no project is selected, up to 5,000 files). When something changed and no diff or commit is open, the panel reads the repository again. While a diff, a commit or a pull request review is open, it keeps the view and asks you to **Refresh** instead. Checks wait while Git holds a lock on its metadata. **Reload Project** opens the selected project again using the Editor's unsaved-edit confirmation. Git inspection uses a read-only adapter and isomorphic-git with index refresh disabled. If the repository changes during a read, refresh after the other operation completes.

When the host passes `localWrite`, the panel can also add files to the next record (stage), remove them from it (unstage) and record the staged changes (commit) on the current branch. Like pull, these operations collect Git's writes first and apply them only after the files they replace are checked again; a failure part way puts back what was applied. They write only `.git/index`, objects and the current branch ref; the work tree and `.git/config` are never written. Commits use the repository's `user.name` and `user.email`; `localWrite.author()` fills in only what the config lacks, and is never written to it. Staging waits until the Editor's edits are saved. The browser cannot see executable bits or symbolic links, so files that Git records with another mode than `100644` cannot be staged here. Operations stop while another tool holds `index.lock` or is in the middle of a merge, cherry-pick, revert or rebase. With `localWrite`, the side list also shows the local branches with **Switch**, a form to create a branch at HEAD (optionally switching to it), and **Create and Switch** for branches fetched from `origin` that have no local branch yet. Switching rewrites HEAD, the index and the work tree through the same checked path, so it needs a stopped project, no unsaved edits and no changes in the work tree, and refuses branches whose files are not regular `100644` files. A branch made from `origin/<name>` gets no tracking settings, since `.git/config` is never written; fetch, pull and push then use the remote branch of the same name. When the open project folder is not on the target branch, the panel asks first. After switching, **Reload Project** opens the branch's files. Without `localWrite`, the panel only reads.

The history is a graph of the commits reachable from the local branches, `origin/*` and a detached HEAD (not from tags), newest committer time first with every child above its parents, 50 at a time with **Show more**. Lanes are laid out in the panel after [DoltHub's commit graph](https://www.dolthub.com/blog/2024-08-07-drawing-a-commit-graph/) and drawn in SVG; each commit is a button showing its branches (`main`, `origin/main`, the current one marked), author and date. Tab enters the list, ArrowUp and ArrowDown (Home, End) move between commits, Enter or Space selects one to compare it with its first parent. Each commit's **⋯** button (or the context menu key, or Shift+F10) opens its actions: **Copy commit ID**, and with `localWrite` **Create branch here…** (a name, optionally switching to it), **Switch to** a local branch at that commit, and **Create and switch to** an `origin/<name>` there without a local branch. They take the same checked path, guards and confirmations as the branch list. `Repository.history({limit, after})` reads the pages and `HistoryGraph` draws them, for hosts that show the history elsewhere; `layoutHistory` is the layout alone.

A Chromium-based browser with File System Access support is required. The first version supports ordinary `.git` directories and content changes. Linked worktrees, submodules, and symbolic links are outside this scope. The browser cannot detect working-tree executable-bit changes. Recorded index and tree modes remain visible. Binary assets show sizes, and text diff generation is bounded.

Use Node.js 26, run `npm ci`, then `npm test`. Vite builds the library and stylesheet, and TypeScript emits declarations. `npm pack` prepares the artifact used by the Editor build. `npm run test:browser` runs the branch button's menu and keyboard (also beside the panel on a real repository), the history graph's keyboard and actions, and the comparison dialog's block drawing, in Chromium on the minimal editor runtime (`@kubohiroya/turbowarp-plus-editor-test-runtime`), with the Editor's pinned VM and Scratch Blocks and without building the Editor. The Editor enables the panel by default. Start it with `twPlusLocalGit=0` in its URL to disable the integration; the branch button is then not shown.

The panel structure and local Git approach were informed by [duff](https://github.com/chigichan24/duff). The implementation uses [isomorphic-git](https://github.com/isomorphic-git/isomorphic-git) and [react-diff-view](https://github.com/otakustay/react-diff-view). Bundled licenses are listed in the build's third-party notices.

## Smart HTTP adapter

`test/smart-http-fixture.js` runs `git-http-backend` on the IPv4 loopback for tests. It uses only Node.js built-in modules and ships in the package so browser tests of a host use the fixture of the same version.

Import `createGitSmartHttp` from `@kubohiroya/turbowarp-plus-editor-git/smart-http`. Pass the selected GitHub HTTPS remote from Git config, a trusted connection (`mode` and `proxyOrigin`), and a function that returns the current proxy session or `null`. A `GitAuthProvider` from the auth package satisfies this contract. The Git package takes these types from the auth package, which is an optional peer: only TypeScript users need it installed, and the read-only panel and the adapter run without it.

```ts
const transport = createGitSmartHttp({
    remote: configuredRemoteUrl,
    connection: provider.connection,
    getSession: () => provider.getSession()
});
await git.fetch({fs, dir, remote: remoteName, ...transport});
```

Pass the same transport options to `git.fastForward` for fast-forward-only pulls and to `git.push` with `force: false` for explicit pushes. Keep the existing worktree safety checks in the caller. The adapter writes no Git configuration and sends only proxy credentials to the fixed proxy. It maps Git discovery and RPC requests to `/v1/git/<owner>/<repo>.git/`. Requests have a 32 MiB cap, which the caller can lower, and successful responses stream back to isomorphic-git. A `PUSH_OUTCOME_UNKNOWN` error means the remote ref must be checked before another push.

Each receive-pack POST carries a new UUID v4 in `Git-Push-Id`. A browser replay carries the same ID. The proxy's `409 PUSH_DUPLICATE` is exposed as `PUSH_OUTCOME_UNKNOWN` so the caller can reconcile the remote ref with a fetch.

`npm test` runs the local Git tests and a headless Smart HTTP fixture on IPv4 loopback using `git-http-backend`. The fixture uses disposable repositories and test credentials. [Proxy, authentication and CORS contract](https://github.com/kubohiroya/turbowarp-plus-editor/issues/315).

When the Editor host supplies connection settings, the Local Git panel offers fetch, fast-forward pull and push for the current branch and its existing GitHub HTTPS `origin`. Authorize push when connecting to enable the explicit push action. Fetch updates Git metadata. Pull requires a stopped project, a clean worktree, and regular non-executable files. Pull stages the changes, rechecks the local state, and then applies them. Reopen the project from the panel after a successful pull.

### Pull requests over the connection

While the connection is connected, the pull request review reads a pull request's contents over the same Git Smart HTTP route instead of the GitHub API, so private repositories work and the API rate limit is not used for contents. `repository.fetchPullRequest(number, getSession, guard, signal)` fetches GitHub's `refs/pull/<number>/head`, which the base repository also exposes for pull requests from forks, together with every branch (two requests: one advertisement and one pack). The branches update `refs/remotes/origin/*` as fetch does. `repository.readPullRequest(head, {sha, branch})` then compares the head with its merge base against the base, from local Git objects: the changed paths (with exact renames paired), each `project.source.json` as a block diff, and thumbnails from the same commits. The proxy routes and the GitHub App permissions are unchanged.

The fetched head is kept at `refs/pull/origin/<number>/head`, replaced on each fetch of that pull request (heads can be force-pushed). Outside `refs/heads`, `refs/remotes` and `refs/tags`, Git CLI shows it in `git for-each-ref refs/pull` and `git log --all` but not in `git branch -a` or `git tag`; `git fetch --prune` does not remove it, unlike a ref under `refs/remotes/origin/`, which would also read as a branch on GitHub; and `git gc` keeps its objects, which a fetch without a ref would leave unreachable. Remove the refs with `git update-ref -d refs/pull/origin/<number>/head` when they are no longer needed. The fetch writes only objects and refs through the same staging and lock (`tw-plus-git-mutation`) as fetch and pull, never the work tree, the index, HEAD or `.git/config`.

Select a pull request directly from the list. Each row shows an icon, a colored number and a status label. The public API supplies the list, title, description and base for public repositories. If the public list is unavailable and a GitHub connection is active, the panel tries the connection proxy. If neither API is available, the panel lists the PR numbers advertised over Git. It compares with the recorded base commit or branch when available. Otherwise it starts with the default branch and lets you choose another base. A pull request already merged into the chosen branch shows no changes unless the API supplied its base commit.

#### Running a pull request locally

With `localWrite`, a pull request read over the connection offers **Open here as pr/&lt;number&gt;**. It creates the local branch `pr/<number>` at the fetched head (`pullRequestBranch(number)`; `refs/pull/origin/<number>/head` stays as it is), switches to it through the same checked path as the branch list, and opens the selected project folder again from it, so the pull request's version can be run in the Editor. It is refused, and nothing is written, while the project runs, while the Editor has unsaved edits, or while the work tree has changes (staged, unstaged or untracked). It asks first when the open project folder is not in the pull request. If `pr/<number>` already exists at the same commit, the panel switches to it; if it points at another commit (you recorded on it, or the pull request moved), the panel refuses and leaves the branch unchanged. Switch to it from **Record locally**, or rename or delete it with Git (`git branch -m pr/<number> <name>`, `git branch -D pr/<number>`), and open the pull request again. The button is not shown for pull requests read from the public API, which brings no Git objects, nor without `localWrite`.

#### Sending a review

When the connection was made with **Allow sending reviews** (the auth package's optional `review` grant, separate from push), a pull request read over the connection offers a comment field under each code change and a **Send a review** box: an overall comment and **Comment**, **Approve** or **Request changes**. The host's `connection` passes `reviewGranted()`. The review goes through the proxy's GitHub API routes (`/v1/github/<owner>/<repo>/`, `createGitHubReviewApi`), which keep the GitHub token and node IDs; the client sends the Bearer of the proxy session, a `Review-Submit-Id`, the pull request number, the fetched head and the words. With the GraphQL routes, one review is sent in steps one at a time: a pending review on the fetched head, one file-level thread on the `project.source.json` per code comment (up to 50), then the submission. Comments on files outside the pull request's changes, beyond 50, or on a file GitHub refused go in the review body under their file and script; the box shows how many go where before sending. When the proxy answers `404 GITHUB_API_UNAVAILABLE` for the GraphQL routes, the whole review goes in the body of one REST review instead; when neither route is available, sending is not offered.

A failure before the submission discards the pending review, so nothing is published. If that fails, the box says a pending review remains on GitHub and offers to discard it. A refused submission keeps the pending review with its threads, to change and send again or discard. When the outcome is unknown (a lost answer, a duplicate, `502`/`504`), nothing is sent again on its own: **Check Whether It Was Sent** reads the proxy's record. A rate limit shows its wait and disables the buttons for it. The draft (words, result, and an in-progress submission ID) is kept in browser storage under `turbowarp-plus-git:review-draft:<owner/repo#number>` until GitHub has the review, through failures and reloads; it never holds tokens, the proxy address or GitHub IDs. `sendReview`, `checkReview`, `discardReview`, `planReview` and the draft functions are exported from `./project-source-diff` apart from React.

The branch you were on stays as it was. To go back, switch to it under **Record locally** (the panel names it after opening). `pr/<number>` is an ordinary local branch without tracking settings: the panel does not delete it, and pull and push treat it like any other branch, so do not push it unless you mean to. Delete it with `git branch -D pr/<number>` when it is no longer needed.

## Comparing before choosing

`openProjectComparison(document, options)` lays several titled comparisons of `project.source.json` texts in one modal and asks the user to choose an action. Each of `sections` takes the same `before` and `after` as `ProjectSourceComparison`. The promise resolves with the chosen action's `id`, or with `null` when the dialog is closed or Escape is pressed. The first action receives focus, so list the one that loses the least first. The project folder uses it to show "Your unsaved edits" next to "Changes in the folder" before replacing unsaved edits.

```ts
const choice = await openProjectComparison(document, {
    title: 'External changes and your unsaved edits',
    sections: [{title: 'Your unsaved edits', before: base, after: edited}, {title: 'Changes in the folder', before: base, after: disk}],
    actions: [{id: 'keep', label: 'Keep My Edits'}, {id: 'discard', label: 'Discard Edits and Load from Folder'}],
    renderBlock
});
```

## Release

`.github/workflows/release.yml` publishes to npm. Push a `v<version>` tag that names the
`package.json` version on a `main` commit: the workflow runs the tests, packs the archive, attaches it
to the GitHub Release, publishes it to npm and points `latest` and `next` at it. It authenticates with
npm Trusted Publishing (OIDC), not a token, and publishes with provenance. The npm settings name this
workflow file, so rename both together.
